# Technoledge Co. 业务类型目录

## 1. 文档状态

- 里程碑：M2（能力需求分析）
- 状态：首轮分析已完成，持续维护
- M2 完成日期：2026-08-13
- 适用范围：`packages/company/spec/organization.yaml` 中定义的全部 Position
- 维护单位：业务类型；不按 Agent 实例分别维护
- 上游依据：组织定义、组织说明和核心数据契约
- 下游用途：为 M3 的业务规则、权限边界和运行记录，以及后续 Tool、Skill 和员工能力设计提供可追溯输入

本文是业务类型属性的统一记录位置。业务类型用于人工分析和规划，不是运行时对象；其名称、编号或内容不得直接用于权限判断、工作流分支或数据库类型判定。

本目录的目的，是从常见业务中识别后续所需的 Tool、Skill、数据、协作和运行能力，而不是把员工工作固化为标准作业程序（SOP）。除非后续规则明确规定，条目中的步骤、协作方式和候选能力均为参考分析，不是穷举清单或强制执行顺序。员工仍应依据岗位职责、实际上下文和专业判断主动开展工作；业务目录不得成为限制合理行动或免除判断责任的依据。

## 2. 记录边界

本目录在 M2 回答：

- 谁发起、谁负责、业务为什么开始。
- 业务需要什么输入，经过哪些主要步骤，产出什么。
- 结果交给谁，出现什么情况时需要协作或升级。
- 怎样判断业务完成。
- 后续可能需要哪些数据、动作、Tool、Skill、审批和运行记录。

本目录不在 M2 决定：

- 某岗位是否有权执行某项动作，以及可执行的具体范围。
- 谁拥有审批权，审批是否可以委托。
- Token 预算、超限行为、数据保留周期和凭证管理方式。
- 数据库表、Tool 接口、工作流状态机或 Agent Prompt 的最终实现。
- 员工处理具体事项时必须遵循的固定步骤、唯一方法或完整行动清单。

以上内容在本目录中只能标记为“候选”或“待决策”，由 M3 形成明确规则后再实现。

## 3. 编写约定

### 3.1 业务类型编号

每个条目使用文档级稳定编号：`<position-id>/<business-slug>`，例如：

```text
finance.token-accountant/monthly-token-cost-report
```

编号只用于文档引用和后续规则追溯。岗位必须引用 `organization.yaml` 中的 Position ID；业务短名使用小写英文和连字符。业务改名时保留编号，业务拆分或合并时创建新编号并在原条目记录替代关系。

### 3.2 状态

| 状态 | 含义 |
|---|---|
| 待细化 | 仅确认业务名称和主责岗位 |
| 待评审 | 属性已填写，尚未确认边界和交接 |
| 已确认 | 已通过 M2 业务评审，可作为 M3 输入 |
| 暂缓 | 当前里程碑暂无业务定义，保留条目供后续恢复 |
| 已合并 | 内容已由另一个业务条目承接，不再独立进入后续设计 |
| 已废弃 | 不再使用，并已记录原因和替代条目 |

### 3.3 填写规则

- 一个条目只描述一个可重复发生、具有明确完成结果的业务类型。
- “输入”和“产出”写业务信息或 Artifact，不预先设计数据库表。
- “主要步骤”描述正常业务路径，不写实现代码或未经确认的权限结论。
- “主要步骤”是帮助识别能力需求的典型路径，不是必须逐项执行的 SOP；员工可以根据岗位和实际情况调整、补充或省略非必要步骤。
- 每个交接写清交出方、接收方、交接内容和接收条件。
- 数据、动作、Tool、Skill、外部服务和审批均先记为候选，保留其业务原因。
- 候选 Tool 和 Skill 应支持员工判断与执行，不应把业务名称映射为固定流程或限制员工只能采取已列出的动作。
- 不确定内容写入“待决策事项”，不得用模糊措辞假装已经确认。

## 5. 业务条目

### `executive.general-manager/major-business-decision`：重大经营决策

#### 基本信息

| 属性 | 内容 |
|---|---|
| 状态 | 已确认 |
| 版本 | 1 |
| 主责岗位 | `executive.general-manager` |
| 业务目标 | 对需要 CEO 承担最终责任的公司事项作出明确决定 |
| 首版范围 | 公司运转异常，以及可能提高效率或降低成本且被大秘书判断为重大的事项 |
| 非目标 | 非重大事项的具体处置；CEO 决定的执行和跟踪 |
| 发生方式 | 事件触发 |

#### 启动与输入

| 属性 | 内容 |
|---|---|
| 触发条件 | 大秘书发现或收到需要决策的事项，并自行评估为重大事项 |
| 发起方 | `administration.chief-secretary` |
| 必要输入 | 能够向 CEO 说明待决事项及其对运转、效率或成本影响的信息 |
| 可选输入 | 相关部门提供的分析、备选方案和补充材料 |
| 前置业务状态 | 大秘书已经完成重大性判断，并认定事项需要 CEO 决策 |

#### 正常处理

1. 大秘书收集公司运转异常或效率、成本改进事项的相关信息。
2. 大秘书自行判断事项是否重大。
3. 非重大事项由大秘书或相关部门自行决策，并将决定纳入大秘书提交给 CEO 的简报；该分支不进入重大经营决策。
4. 对重大事项，大秘书向 CEO 汇报待决事项及其影响。
5. CEO 作出明确决定，本业务随即完成。
6. 大秘书随后记录该决定，并通过 `administration.chief-secretary/decision-follow-up` 跟进落实；记录和跟进不是本业务的完成门槛。

#### 产出与完成

| 属性 | 内容 |
|---|---|
| 必要产出 | CEO 对所汇报重大事项作出的明确决定 |
| 产出接收方 | `administration.chief-secretary` |
| 验收标准 | CEO 已对待决事项明确表达决定；不以决定是否已经执行作为完成条件 |
| 完成证据 | 能够还原 CEO 决定内容及其对应事项的消息或记录；具体形式待 M3 决定 |
| 后续业务 | `administration.chief-secretary/decision-follow-up` |

#### 协作与交接

| 交出方 | 接收方 | 交接内容 | 接收条件 |
|---|---|---|---|
| 相关部门 | `administration.chief-secretary` | 运转异常或效率、成本改进事项及相关信息 | 大秘书已获得足以进行重大性判断的信息 |
| `administration.chief-secretary` | `executive.general-manager` | 被判断为重大的待决事项及其影响 | CEO 已收到并能够识别需要决定的问题 |
| `executive.general-manager` | `administration.chief-secretary` | 明确决定 | CEO 已表达决定，本业务完成并进入后续记录和跟进 |

#### 异常与升级

| 情况 | 当前责任方 | 预期处理 | 升级对象 | 升级条件 |
|---|---|---|---|---|
| 信息不足，无法完成重大性判断 | `administration.chief-secretary` | 尚未定义，记录为信息缺口 | `executive.general-manager` 或相关部门，待决定 | 待决定 |
| 大秘书无法判断事项是否重大 | `administration.chief-secretary` | 尚未定义，记录为责任边界缺口 | `executive.general-manager` | 待决定 |
| CEO 未在需要的时间内作出决定 | `executive.general-manager` | 尚未定义，记录为时限和降级路径缺口 | 无更高岗位 | 待决定 |

#### M3 候选需求

本节只记录业务依据，不授予权限。

**业务动作**

| 动作 | 执行候选岗位 | 对象与范围 | 业务原因 | 副作用级别 |
|---|---|---|---|---|
| 收集和读取事项信息 | `administration.chief-secretary` | 与待决事项相关的内部任务、项目、消息和产物 | 判断事项是否重大并准备汇报 | 只读 |

| 对非重大事项作出决定 | 大秘书或相关部门的候选岗位 | 被判断为非重大的事项；具体范围待 M3 确定 | 避免所有事项都等待 CEO | 内部写入 |
| 记录决定并纳入简报 | `administration.chief-secretary` | CEO 的重大决定，以及大秘书或部门的非重大决定 | 保证 CEO 获知决定并支持后续追踪 | 内部写入 |

|---|---|---|---|---|

| 事项重大性判断 | 创建或修改 | 判断结果、判断者、时间和对应事项 | 解释事项为何提交或未提交 CEO | 当前无对应核心对象，保存方式待 M3 确定 |

| 非重大事项简报记录 | 创建、追加 | 事项、决定、决策岗位和简要结果 | 向 CEO 汇报分散的自主决定 | 汇总周期、格式和保留要求待 M3 确定 |
| `AuditEvent` | 追加 | 重大性判断、提交和决定等关键动作 | 保留决策过程证据 | 只追加；具体审计范围待 M3 确定 |

**Tool 与外部服务**

| Tool 或能力候选 | 用途 | 外部服务 | 是否产生外部副作用 | 失败时的业务影响 |
|---|---|---|---|---|
| 查询待决事项上下文 | 收集重大性判断和决策所需信息 | 无 | 否 | 大秘书或 CEO 无法获得完整背景 |
| 提交重大事项 | 将事项和相关材料交给 CEO | 无 | 否 | CEO 无法收到待决事项 |
| 记录决定 | 保存 CEO 或非重大事项决策者的决定 | 无 | 否 | 决定无法可靠传达、跟进或审计 |
| 写入 CEO 简报 | 汇总非重大事项的自主决定 | 无 | 否 | CEO 无法获知已经发生的分散决策 |

**Skill 候选**

| Skill 候选 | 使用岗位 | 支持的判断或工作 | 不应固化的内容 |
|---|---|---|---|
| 经营事项分析 | `administration.chief-secretary`、`executive.general-manager` | 分析事项对公司运转、效率和成本的影响 | 不替大秘书固定定义何为重大，也不替 CEO 作决定 |
| 决策汇报与摘要 | `administration.chief-secretary` | 整理上下文、备选方案和影响，形成清晰汇报 | 不强制唯一汇报格式或固定结论 |

**成本、风险与审批候选**

| 类别 | 候选事项 | 触发原因 | 未控制的影响 |
|---|---|---|---|
| 成本 | 收集、分析和汇报事项产生的 Token 消耗 | 每次重大性判断和决策准备 | 高频或信息量过大时成本不可控 |
| 风险 | 大秘书误判重大性 | 重大标准由大秘书自行评估且尚无最低记录要求 | 重大事项未提交 CEO，或普通事项过度占用 CEO |
| 风险 | 非重大事项的自主决策范围不清 | 大秘书或各部门可以自行决定，但具体边界尚未定义 | 越权、冲突或不一致决策 |
| 风险 | 决定未被准确记录或进入简报 | 决策完成与后续记录分属不同业务步骤 | 决定丢失、误传或无法追责 |
| 审批 | 是否把部分重大决定建模为 `Approval` | 重大经营决定不一定等同于对某个动作的批准 | 混淆一般决策与审批，导致状态和权限设计错误 |

#### 待决策事项

- 保留大秘书对重大性的自主判断权时，是否仍需规定最低判断依据、记录内容或必须升级的事项类别。
- 大秘书和各部门可以自行决定的非重大事项范围，以及决定冲突时的处理方式。
- 相关部门如何把自主决定交给大秘书并确保进入 CEO 简报。
- 大秘书向 CEO 汇报时的必要内容、证据要求和优先级。
- CEO 未及时决定、要求补充信息、撤回或修改决定时的处理方式。
- CEO 决定和重大性判断使用现有契约对象还是新增业务记录，以及其格式、确认、保留和审计要求。
- 决定的记录、传达和落实跟进由 `administration.chief-secretary/decision-follow-up` 业务继续定义。

### `executive.general-manager/critical-approval`：关键审批

#### 基本信息

| 属性 | 内容 |
|---|---|
| 状态 | 已确认 |
| 版本 | 1 |
| 主责岗位 | `executive.general-manager` |
| 业务目标 | 对具体高危操作作出当次授权、永久授权或拒绝的明确答复 |
| 首版范围 | 需要 CEO 明确授权后才能执行的高危操作指令，例如申请操作电脑上的文件夹 |
| 非目标 | 决定公司经营方向的重大经营决策；不需要 CEO 授权的普通内部操作；获批操作本身的执行 |
| 发生方式 | 事件触发 |

#### 启动与输入

| 属性 | 内容 |
|---|---|
| 触发条件 | 某项具体高危操作在执行前要求获得 CEO 授权 |
| 发起方 | 需要执行高危操作的部门或岗位，经 `administration.chief-secretary` 汇总后提交 |
| 必要输入 | 申请执行的操作、目标对象、申请原因和足以让 CEO 判断风险的上下文 |
| 可选输入 | 预期影响、恢复方式、替代方案和相关证据 |
| 前置业务状态 | 操作尚未执行，审批请求已经发送给大秘书 |

#### 正常处理

1. 申请岗位将高危操作请求发送给大秘书，不直接向 CEO 提交。
2. 大秘书汇总请求及其必要背景，并提交给 CEO。
3. CEO 根据申请内容作出当次有效、永久有效或拒绝三类答复之一；具体授权范围以 CEO 的回复为准。
4. 大秘书接收并记录审批结果，将结果传达给申请方。
5. 当次授权只能用于获批的当前一次操作；永久授权对 CEO 回复所规定的范围持续有效；拒绝时不得执行所申请操作。
6. 审批结果已经明确并可供申请方执行或停止时，本业务完成。获批操作的实际执行属于后续业务或 Tool 调用。

#### 产出与完成

| 属性 | 内容 |
|---|---|
| 必要产出 | CEO 作出的当次有效、永久有效或拒绝结果，以及其适用的操作范围 |
| 产出接收方 | `administration.chief-secretary`，随后由其传达给原申请方 |
| 验收标准 | CEO 已明确给出三类结果之一，结果与原请求相关联，并已由大秘书接收和传达 |
| 完成证据 | 能够还原申请内容、申请方、CEO 回复、授权类型和适用范围的 `Approval` 及相关消息或审计记录 |
| 后续业务 | 获批操作对应的业务或 Tool 调用；拒绝时无 |

#### 协作与交接

| 交出方 | 接收方 | 交接内容 | 接收条件 |
|---|---|---|---|

| 风险 | 高危操作分类不完整 | 当前仅有文件夹操作示例，未列出所有必须审批的动作 | 需要审批的操作可能绕过 CEO |

| 风险 | 审批通过后实际操作发生变化 | Tool 输入可能与申请时不同 | 原授权被用于未审批的操作或目标 |

#### 待决策事项

- 哪些操作属于必须由 CEO 审批的高危操作；除文件夹操作外是否包括命令执行、外部发送、发布、付款、凭证或配置变更等。
- 文件夹操作需要审批的具体边界，例如是否区分读取、创建、修改、移动、覆盖和删除。
- CEO 回复需要包含哪些最小信息，系统如何从回复中可靠识别授权类型和精确范围。
- 当次授权的消费、失败重试和幂等规则，以及一次操作由多次 Tool 调用组成时如何判定“当次”。
- 永久授权能否撤销、修改或暂停，由谁发起复审，以及组织、路径、Tool 或风险变化后是否自动失效。
- 审批请求的汇总时机、紧急请求路径、等待时限，以及 CEO 未回复时的处理方式。
- 大秘书是否可以退回信息不足或明显重复的请求，以及合并多个请求时如何保持各自的授权边界。
- 现有 `Approval` 契约如何表达“当次有效”和“永久有效”，以及它与实际 `ToolInvocation` 的关联方式。

### `executive.general-manager/resource-allocation`：资源分配

#### 基本信息

| 属性 | 内容 |
|---|---|
| 状态 | 已确认 |
| 版本 | 1 |
| 主责岗位 | `executive.general-manager` |
| 业务目标 | 根据公司项目需求和日常 Token 消耗，决定是否增加某个供应商的 Token 余额 |
| 首版范围 | 供应商 Token 余额增补申请的 CEO 批准 |
| 非目标 | 给具体部门、项目或 Agent 分配 Token 额度；财务日常成本记录；新项目本身的立项决定；获批后的实际充值操作 |
| 发生方式 | 事件触发 |

#### 启动与输入

| 属性 | 内容 |
|---|---|
| 触发条件 | Token 财务专员根据项目预算和企业日常 Token 花费，判断需要增加某个供应商的 Token 余额 |
| 发起方 | `finance.token-accountant` 向 `administration.chief-secretary` 发起，由大秘书向 CEO 提出 |
| 必要输入 | 目标供应商、当前余额或可用量、项目预算需求、日常消耗分析及增补申请 |
| 可选输入 | 新项目预算估算、历史消耗趋势、异常消耗说明和预计可支持的运行周期 |
| 前置业务状态 | 财务已经完成预算分析，并形成需要 CEO 决定的余额增补申请 |

#### 正常处理

1. 有新项目时，项目经理根据项目情况估算 Token 预算并发送给 Token 财务专员。
2. Token 财务专员汇总项目预算、现有项目情况和企业运转的日常 Token 花费，分析预算与供应商余额是否充足。
3. 财务认为需要增加余额时，向大秘书提交针对某个供应商的 Token 余额增补申请及分析依据。
4. 大秘书汇总申请并向 CEO 提出。
5. CEO 决定是否批准增加该供应商的 Token 余额。
6. 大秘书记录并把决定传达给财务。审批后的实际充值责任方和本业务的最终完成边界尚待决定。

#### 产出与完成

| 属性 | 内容 |
|---|---|
| 必要产出 | CEO 对指定供应商 Token 余额增补申请的批准或拒绝决定 |
| 产出接收方 | `administration.chief-secretary`，随后由其传达给 `finance.token-accountant` |
| 验收标准 | CEO 已对可识别的供应商余额增补申请作出明确决定；是否必须等待充值到账才算完成尚待决定 |
| 完成证据 | 与目标供应商、申请依据和申请记录关联的 CEO 决定，以及大秘书向财务传达结果的记录 |
| 后续业务 | 获批后的供应商余额充值与到账核验；对应业务类型及责任岗位待定义 |

#### 协作与交接

| 交出方 | 接收方 | 交接内容 | 接收条件 |
|---|---|---|---|
| `operations.project-manager` | `finance.token-accountant` | 新项目情况及 Token 预算估算 | 财务已获得可纳入整体预算分析的估算 |
| `finance.token-accountant` | `administration.chief-secretary` | 指定供应商的余额增补申请、项目预算和日常消耗分析 | 大秘书已收到足以向 CEO 提出申请的信息 |
| `administration.chief-secretary` | `executive.general-manager` | 汇总后的余额增补申请 | CEO 能够识别目标供应商、申请原因和预算影响 |
| `executive.general-manager` | `administration.chief-secretary` | 批准或拒绝决定 | 大秘书能够将决定关联到原申请 |
| `administration.chief-secretary` | `finance.token-accountant` | CEO 决定 | 财务已收到可用于后续处理的明确结果 |

#### 异常与升级

| 情况 | 当前责任方 | 预期处理 | 升级对象 | 升级条件 |
|---|---|---|---|---|
| 新项目预算信息不足 | `operations.project-manager` | 补充项目范围、预计工作量或其他估算依据 | `finance.token-accountant` | 财务无法将项目需求纳入预算分析 |
| 财务无法判断应增加哪个供应商或多少余额 | `finance.token-accountant` | 记录分析缺口并补充供应商、价格或消耗信息 | `administration.chief-secretary` | 补充后仍无法形成明确申请时 |

| 余额不足可能导致公司或项目中断 | `finance.token-accountant` | 尚未定义，未获批准前不得假设可以充值 | `administration.chief-secretary`、`executive.general-manager` | 紧急阈值和处置路径待决定 |
| 已批准但充值失败或余额未到账 | 待定义 | 尚未定义，记录为后续执行和补偿机制缺口 | `administration.chief-secretary`、`executive.general-manager` | 待决定 |

| 风险 | 充值对象或额度与审批不一致 | 外部执行与内部申请分离 | 错误充值、超额充值或无法追责 |
| 审批 | 供应商余额增补 | 财务分析认为需要增加余额 | 未经 CEO 同意产生外部成本 |
| 审批 | 充值操作是否还需关键审批 | 余额增补批准与具体付款或高危 Tool 授权可能是不同事项 | 重复审批或未经必要授权直接执行 |

#### 待决策事项

- CEO 批准的是“是否增加余额”还是同时批准目标供应商、具体额度、货币金额和执行期限。
- CEO 拒绝、部分批准或要求调整额度时的表达方式和后续流程。
- CEO 作出决定即视为本业务完成，还是必须等充值成功并确认余额到账后才完成。
- 获批后由哪个岗位或受控系统执行充值，使用什么支付或供应商账户，以及谁负责到账核验。
- 余额充值是否还需要进入 `executive.general-manager/critical-approval`，以及如何避免同一事项重复审批。

- 项目经理估算预算所需的格式、单位、精度、变更和复核方式。
- 多个供应商之间的选择标准，以及价格、模型能力、可用性和已有余额如何共同影响申请。
- 充值失败、重复充值、部分到账、退款和供应商不可用时的补偿与升级路径。

### `administration.chief-secretary/task-intake-and-routing`：任务受理与分流

#### 基本信息

| 属性 | 内容 |
|---|---|
| 状态 | 已确认 |
| 版本 | 1 |
| 主责岗位 | `administration.chief-secretary` |
| 业务目标 | 接收公司内部信息、CEO 指令和任务，将需要处理的事项交给合适的部门或岗位并取得接收确认 |
| 首版范围 | 各部门发送给大秘书的信息，以及 CEO 发送给大秘书的指令和任务 |
| 非目标 | 代替接收岗位执行被分流的业务；使用固定业务名称或硬编码规则作权限判断；持续跟踪任务执行结果 |
| 发生方式 | 事件触发 |

#### 启动与输入

| 属性 | 内容 |
|---|---|
| 触发条件 | 大秘书收到来自公司部门的信息，或收到 CEO 的指令或任务 |
| 发起方 | `executive.general-manager` 或公司各部门中的岗位 |
| 必要输入 | 来源方、信息或任务内容，以及足以识别处理目标和上下文的材料 |
| 可选输入 | 期望结果、优先级、期限、关联项目或任务、相关 Artifact |
| 前置业务状态 | 输入已经到达大秘书的受理入口，且来源方可识别 |

#### 正常处理

1. 大秘书接收并记录来自各部门的信息或来自 CEO 的指令和任务。
2. 大秘书 Agent 根据输入内容、公司上下文和自身模型能力判断事项应交给哪个部门或岗位处理。
3. 大秘书将事项及其必要上下文发送给判断出的接收方。
4. 大秘书等待接收方明确确认接收；仅发送成功不表示本业务完成。
5. 接收方确认接收后，本业务完成，后续执行由接收方负责。
6. 如果大秘书无法判断归属，则将事项提交给 CEO；CEO 指定归属后的再次分流仍需由接收方确认。

#### 产出与完成

| 属性 | 内容 |
|---|---|
| 必要产出 | 明确的接收部门或岗位，以及该接收方的接收确认；无法判断时还包括提交给 CEO 的升级记录 |
| 产出接收方 | 被选定的部门或岗位；无法判断时先由 `executive.general-manager` 接收 |
| 验收标准 | 事项已交给明确的接收方，且该接收方已确认接收 |
| 完成证据 | 原始输入、分流判断、发送记录和接收方确认能够相互关联的消息、任务或审计记录 |
| 后续业务 | 接收岗位负责的具体业务类型；如果需要持续协调或跟踪，则进入相应的大秘书业务 |

1. 大秘书接收部门需求、项目完工通知或其他公司信息，并判断是否属于紧急情况。
2. 对可能影响项目正常进行的紧急事项，例如预算即将耗尽，大秘书主动通过邮件通知 CEO。
3. 对其他事项，大秘书先写入内部文件，不主动逐项汇报。
4. CEO 请求相关信息时，大秘书从记录及必要的公司上下文中整理内容并向 CEO 汇报。
5. 紧急邮件已发出，或非紧急信息已记录且能在 CEO 请求时被检索，即完成对应信息的处理。

#### 正常处理

以下是能力分析参考，不限制运营保障专员根据故障特点自主选择诊断和修复方式。

1. 运营保障专员按计划运行规定范围的单元测试。
2. 如果单元测试通过，本次检测完成。
3. 如果单元测试失败，运营保障专员读取结果和必要上下文，自行诊断并处理故障。

5. 如果运营保障专员无法处理，则把故障、影响、已尝试内容和测试证据发送给大秘书。
6. 大秘书将该事项作为紧急事件汇报 CEO；升级后原故障的最终关闭方式尚待决定。

### `finance.token-accountant/on-demand-token-report`：按需 Token 汇总报告

#### 基本信息

| 属性 | 内容 |
|---|---|
| 状态 | 已确认 |
| 版本 | 1 |
| 主责岗位 | `finance.token-accountant` |
| 业务目标 | 在 CEO 请求时即时汇总公司 Token 消耗，使其能够查看各部门在各模型上的 Token 使用情况 |
| 首版范围 | 基于数据库中 `CostRecord` 的部门与模型交叉汇总 |
| 非目标 | 固定周期自动生成报告；没有请求时主动提交报告；报告 Pi 估算金额或供应商实际货币账单 |
| 发生方式 | CEO 请求触发 |

#### 启动与输入

| 属性 | 内容 |
|---|---|
| 触发条件 | CEO 请求查看 Token 消耗情况 |
| 发起方 | `executive.general-manager`，经公司信息请求入口交给 `finance.token-accountant` |
| 必要输入 | CEO 的报告请求，以及数据库中的 `CostRecord` 和 Agent 到部门的可追溯关系 |
| 可选输入 | CEO 指定的时间范围、部门、模型、项目或其他筛选条件 |

#### 正常处理

以下是能力分析参考，不限制财务根据 CEO 的具体问题调整筛选、分析和呈现方式。

1. 财务接收 CEO 的 Token 消耗查询请求。
2. 财务根据请求即时查询数据库中的 `CostRecord`，不依赖预先生成的周期快照。
3. 财务把消耗关联到部门和模型，并至少形成“部门 × 模型”的交叉汇总，例如研发部在各模型上分别消耗多少 Token。
4. 财务根据请求补充必要的总计、筛选说明和数据缺口，并向 CEO 汇报。
5. CEO 已收到能够回答其请求的汇总结果后，本业务完成；报告无需在无请求时主动提交。

| 属性 | 内容 |
|---|---|
| 必要产出 | 回答 CEO 请求的 Token 汇总，其中至少可按部门和模型两个维度交叉查看消耗量 |
| 产出接收方 | `executive.general-manager` |
| 验收标准 | 报告基于可追溯的 `CostRecord`，能够说明所用范围，并回答各部门在各模型上消耗多少 Token |
| 完成证据 | CEO 请求、查询条件、汇总结果及其生成时间；是否持久化报告 Artifact 待决定 |
| 后续业务 | 发现异常时进入异常消耗调查；余额或预算不足时可进入资源分配或风险汇总与升级 |

#### 正常处理

以下是能力分析参考，不限制项目经理根据需求特点主动澄清、分析和组织 Plan。

1. 项目经理从大秘书接收任务和已有需求上下文。
2. 项目经理根据任务内容自行分析和澄清必要信息，形成 Plan。
3. 项目经理把 Plan 发送给大秘书，大秘书再提交 CEO 审核。

5. 项目经理根据意见修改 Plan，并经秘书再次提交 CEO；必要时重复迭代。
6. CEO 明确批准 Plan 时，本业务完成。
7. 获批 Plan 随后由项目经理交给研发部执行；实际执行属于后续业务。

#### 待决策事项

- Plan 至少需要说明哪些内容，例如目标、范围、任务、验收、风险、预算和依赖。
- 项目经理可以向谁直接澄清信息，是否所有沟通必须经大秘书。
- CEO 审核结果使用 `Approval` 还是一般决定记录，以及批准是否可以附带条件。
- Plan 的格式、存储位置、版本号和批准版本锁定方式。
- CEO 审核时限、提醒、终止需求和最大修改轮次。
- CEO 批准后研发部如何确认接收，以及使用岗位池还是具体研发岗位作为接收方。
- 获批 Plan 中涉及高危操作、外部写入或新增 Token 余额时是否仍需分别进入关键审批或资源分配。

### `operations.project-manager/task-decomposition-and-delegation`：任务拆分与分派

#### 基本信息

| 属性 | 内容 |
|---|---|
| 状态 | 已确认 |
| 版本 | 5 |
| 主责岗位 | `operations.project-manager` |
| 业务目标 | 由项目经理根据项目需要自主拆分工作，并通过现有 Pi `subagent` 能力交给研发 Agent 完成方案设计、开发实现、测试验证、缺陷修复或安全评估并返回结果 |

| 非目标 | 重新实现一套 subagent 执行器；把一种拆分方式固化为项目管理 SOP；仅凭业务目录扩大研发 Agent 的 Tool 或数据权限 |

#### 启动与输入

| 属性 | 内容 |
|---|---|
| 触发条件 | 项目经理取得 CEO 已批准的 Plan，并判断需要调用研发 subagent 执行其中的工作 |
| 发起方 | `operations.project-manager` |
| 必要输入 | 获批 Plan、要委派的任务描述和可用研发 Agent 定义 |
| 可选输入 | 工作目录、模型与思考级别、工具范围、并行或链式安排及必要上下文 |
| 前置业务状态 | 使用的是 CEO 已批准的 Plan 版本，`subagent` 扩展已安装并可调用 |

#### 正常处理

任务拆分、执行顺序和 Agent 选择由项目经理根据 Plan 与实际情况判断，不在本目录中规定固定流程。

1. 项目经理从获批 Plan 中识别适合委派给研发 Agent 的工作。
2. 项目经理根据任务需要选择合适的研发 Agent，并使用现有 `subagent` 工具完成方案设计、代码实现、测试用例编写与执行、根据测试问题修改缺陷或基本软件安全分析。
3. `subagent` 扩展为每次调用启动独立 Pi 进程，在隔离上下文中执行任务，并向项目经理持续返回进度和最终结果。
4. 项目经理根据返回结果自主决定是否继续委派、补充任务、调整拆分或进入成果验收。
5. 现有扩展负责子任务执行、失败返回和中止传播；公司层只补充业务归属、权限、Token 记录和审计衔接。

#### 产出与完成

| 属性 | 内容 |
|---|---|
| 必要产出 | `subagent` 调用返回的研发结果，或可识别的失败、中止信息 |
| 产出接收方 | `operations.project-manager` |
| 验收标准 | 现有 Harness 已完成项目经理发起的 subagent 调用并返回结果状态；业务成果是否合格由后续成果验收判断 |
| 完成证据 | 获批 Plan、委派任务、目标 Agent、调用结果、Token usage 和对应公司 Task 或审计关联 |
| 后续业务 | 成果验收与项目汇报，或项目经理根据 Harness 进度和风险信息判断需要的再次委派 |

| subagent 返回失败 | `operations.project-manager` | 根据错误和项目上下文决定重试、调整任务、改派或停止 | `administration.chief-secretary` 候选 | 是否升级由项目影响和项目经理判断 |

#### 待决策事项

- 完工报告至少需要包含哪些信息，例如项目目标、成果引用、验收结论、未解决事项、Token 消耗和后续建议。
- 不同项目需要形成哪些技术文档，以及文档存放位置、更新责任和保留周期。
- 项目经理的验收结果使用独立记录、`Task` 状态、`Message` 还是 Artifact 表达。
- 项目在项目经理验收时、报告发送时还是大秘书确认接收时变为 completed。
- 大秘书接收确认的格式、时限，以及报告信息不足时能否退回。
- 未通过成果的再次调用、修改轮次、部分验收、停止和升级方式。
- 对代码、测试、安全或其他专业成果是否需要相应研发 Agent 提供复核证据，但最终仍由项目经理验收。
- 如何保存超过 Harness 模型可见输出上限的完整成果，确保项目经理基于完整证据判断。
- 完工报告何时属于紧急信息并需要由大秘书主动邮件通知 CEO。

## 7. 后续提取规则

只有状态为“已确认”的业务条目可以作为后续设计依据。进入 M3 或后续 Tool、Skill 和员工能力设计时按以下方式提取：

| M2 内容 | 后续产物 |
|---|---|
| 业务动作、对象与范围 | 岗位操作与数据范围表 |
| 协作与交接 | 通信、任务分派和协助请求规则 |
| 异常与升级 | 升级路径、人工接管和超限处理规则 |
| 外部副作用和审批候选 | 审批事项、审批人和有效期规则 |
| 数据与记录候选 | SQLite 存储范围、追加或更新约束、保留需求 |
| Tool 与外部服务候选 | Tool 边界、授权入口、幂等和审计需求 |
| Skill 候选 | 后续岗位 Skill、知识支持和判断辅助需求；不得据此生成固定 SOP |
| 成本候选 | Token 预算维度、计量和超限行为 |
| 验收标准与完成证据 | 状态转换、Artifact 和审计证据需求 |

提取后的每条 M3 规则应反向引用至少一个业务类型编号。业务目录与 M3 规则发生冲突时，先修订并重新评审业务条目，不在实现代码中隐式补充业务规则。
